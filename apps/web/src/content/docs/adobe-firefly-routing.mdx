---
title: 统一媒体号池与 Adobe 路由
description: Adobe 成员如何与 API 成员在同一分组中按显式模型能力参与统一调度。
---

Adobe 不再拥有独立顶层号池。管理员在统一媒体号池中创建 `type=adobe` 成员，并按上游
接入方式选择 `gateway` 或 `direct`；它与同组 `type=api` 成员共享优先级、并发、健康、
冷却、获租计数和调度指标。

## 候选资格

每个成员必须显式声明 `supportedModelIds`。请求到达指定分组后，调度器先检查成员状态、
分组权限、冷却、容量和模型能力，再对全部合格成员应用当前全局策略。

模型 ID 只是能力键。调度器不会从模型前缀或家族名称推断成员类型，也不会因为一个成员是
Adobe 就自动认为它支持某个模型。同一分组的 API 与 Adobe 成员声明相同图片模型时，二者
进入同一个候选集合。

## Adobe 模式

- `gateway`：调用管理员配置的 Adobe 兼容网关，由成员配置保存鉴权与参数映射。
- `direct`：每个顶层成员保存一个 Adobe 账号的 Cookie 与短期 Token，并通过 Adobe
  专用上游代理访问代码内允许的 HTTPS 主机。

当前视频执行协议只由具备相应显式模型能力的 Adobe direct 成员实现。该限制来自可执行
协议和能力声明，而不是模型名称分流。

## 调度与恢复

全局策略可选择 `priority`、`least_acquired` 或 `least_load`。图片和视频都没有会话
粘性；明确的提交前可切换失败会在同组剩余成员中重选。

视频一旦取得上游任务标识或轮询地址，就固定原 Adobe 成员。后台 worker 只刷新该成员的
一对一凭据并恢复原任务，不跨成员重投。提交结果不确定时保留诊断状态，不自动重投或退款。

完整排序、租约与指标契约见
[统一媒体号池调度](/docs/system#scheduling)。
