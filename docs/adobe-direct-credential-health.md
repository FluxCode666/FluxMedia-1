# Adobe Direct 凭据健康与通知运维

本文说明 Adobe Direct 成员的定时探测、失败复检、隔离、通知和同账号重新授权流程。
系统不保存 Adobe 账号密码，也不执行浏览器自动登录、MFA、验证码、设备验证或风控绕过。

## 能力边界

Adobe Cookie 的真实有效期由 Adobe 控制，系统不能保证“永久不失效”。当前实现通过定时
双 Profile 探测和业务调用时的被动发现，尽快识别凭据失效并停止把新任务调度到故障成员。

- Express 与 Firefly 在同一轮验证，只产生一次成员级结果。
- 健康检查不创建图片、视频、上传或余额消费任务。
- 正常与隔离成员的常规检查窗口为 45–50 分钟。
- 内部扫描任务每 1 分钟认领一次到期成员；多实例通过持久 claim 避免重复提交。
- 业务调用发现凭据失败时可以立即触发被动评估和告警。
- 功能受全局 `INTERNAL_JOB_SCHEDULER_ENABLED` 开关控制。

## 状态与复检

| 状态 | 含义 | 运营动作 |
| --- | --- | --- |
| `pending` | 尚未完成首次双 Profile 检查 | 可等待定时任务或点击“立即检查” |
| `healthy` | 最近一轮双 Profile 均验证成功 | 无需处理 |
| `degraded` | 第一次或第二次成员侧失败 | 系统分别在 5 分钟、15 分钟后复检 |
| `isolated` | 连续第三次成员侧失败 | 新租约已停止，需要同账号重新授权 |
| `overdue` | 超过预期窗口仍未完成评估 | 立即检查调度、数据库、代理与 Adobe 上游 |

隔离状态独立于管理员的“启用成员”开关：隔离只阻止新租约，不中断已有租约，也不阻止
已有租约续租或 `takeoverLease`。重新授权不会自动启用管理员已停用的成员。

平台故障，例如数据库不可用或专用代理未配置，不推进成员连续失败计数。Adobe 鉴权拒绝、
超时、限流、临时上游错误及已配置代理的网络故障会按成员故障策略处理。

## 通知配置

超级管理员在“管理后台 → 系统设置 → 邮件 → Adobe 凭据通知”配置通知模块。

邮件渠道只有在以下两项同时完整时启用：

- 至少一个合法告警收件人；
- 已配置可用的 SMTP 或 Resend 邮件供应商。

Webhook 渠道只有在以下三项同时完整时启用：

- 页面保存了公网 HTTPS 地址；
- 地址通过 DNS、公网 IP、私网/保留地址和隐式凭据校验；
- 部署环境设置了至少 32 字节的 `ADOBE_CREDENTIAL_WEBHOOK_HMAC_SECRET`。

Webhook 地址不允许 userinfo、query 或 fragment，投递拒绝全部 3xx。HMAC 密钥只存在
`.env.local` 或部署环境，系统设置页只显示“已配置/未配置”，不会读取、保存或返回明文。
页面不提供测试通知按钮。

任一渠道配置不完整时，该渠道显示“未配置”，且新事件不会生成该渠道的失败投递行。
邮件与 Webhook 相互独立，一个渠道失败不会阻止成员隔离、恢复或另一个渠道成功。

## 告警投递与保留

成员第三次失败进入隔离，或管理员重新授权恢复时，状态、incident 与已配置渠道的 outbox
在同一事务提交。提交后立即 best-effort 投递；每 1 分钟的补偿任务继续认领到期投递。

- 最多尝试 8 次；
- 退避从 30 秒开始，最长 15 分钟；
- Webhook 和 Resend 携带稳定事件/投递幂等标识；
- SMTP 在远端已接受、进程尚未确认的极小崩溃窗口可能重复投递同一逻辑事件；
- 配置 revision 变化后，旧 pending 投递不会改投新目标，而会进入配置已变更终态；
- 终态评估、incident 和投递历史保留 90 天，由每日任务按依赖顺序清理。

系统设置通知模块显示每个渠道的待投递、重试中、最终失败和最近成功时间，便于运营定位
渠道配置与供应商故障。

## 重新授权

在管理员号池页找到 Adobe Direct 成员：

1. 查看凭据健康状态和下一次检查时间；
2. 必要时点击“立即检查”确认当前状态；
3. 在已登录同一 Adobe 账号的浏览器中使用 Cookie 导出插件重新导出；
4. 点击“重新授权”，粘贴 Cookie 字符串或插件 JSON；
5. 系统在事务外验证 Express 与 Firefly 的稳定账号 ID；
6. 只有两个 Profile 都属于成员原 Adobe 账号时，系统才更新 Cookie、清除隔离并关闭事件。

换账号、稳定账号 ID 缺失、访客会话或任一 Profile 失败都会 fail-closed，旧凭据和隔离状态
保持不变。普通隔离探测即使暂时成功也不会自动恢复，只有同账号重新授权可以恢复调度资格。

## `overdue` 排查

按以下顺序检查：

1. 确认 `INTERNAL_JOB_SCHEDULER_ENABLED=true`；
2. 确认 Web 进程持续运行，健康扫描任务每 1 分钟有执行记录；
3. 检查数据库连接、任务 advisory lock 和到期 claim 是否能释放或重领；
4. 确认 Adobe 专用代理 URL 与密钥配置完整；
5. 检查 Adobe 429、超时和上游延迟是否导致 backlog；
6. 在号池页对单成员执行“立即检查”，区分平台故障与成员凭据故障；
7. 检查 overdue 数、outbox backlog、每渠道最终失败数和健康评估成功率。

不要通过手工修改数据库状态解除隔离。若 Cookie 已失效，按同账号重新授权流程恢复。

## 诊断与敏感信息

Adobe 错误摘要只在管理员号池配置页默认折叠展示，并严格限制为 HTTP 状态、Adobe 错误码、
有限消息和可信请求 ID。React 以纯文本转义显示这些字段。

Cookie、Token、Authorization、账号密码、代理密钥、Webhook HMAC、完整上游响应和未经清洗的
Adobe 错误不得进入普通 DTO、下游响应、日志、邮件、Webhook 或任务结果。发现任何凭据泄露
时应立即轮换对应 Cookie、Token 或部署密钥，并检查数据库备份和日志保留范围。

## 上线检查

- 已执行 Adobe 凭据健康数据库迁移；
- 内部任务调度开关符合部署预期；
- 所有现有 Adobe Direct 成员可从 `pending` 完成首次检查；
- 通知为空时不会产生失败投递；
- 启用邮件前确认供应商和收件人完整；
- 启用 Webhook 前确认公网 HTTPS、接收方验签、时间窗口和事件 ID 去重；
- 管理员停用、健康隔离和重新授权三类状态在号池页可分别识别；
- 监控健康成功率、隔离/overdue 数、Adobe 429/超时、outbox backlog 和最终失败数。
